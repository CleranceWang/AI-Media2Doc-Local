## 2. 核心改造一：ASR 从云端换到本机

### 2.1 上游是怎么工作的

```
浏览器 → presigned PUT → S3（上传音频 mp3）
后端   → generate_download_url() → 得到一个公网可访问的音频 URL
后端   → POST https://openspeech.bytedance.com/api/v1/auc/submit  {audio: {url: ...}}
       ← 返回 task_id
前端   → 轮询 GET /api/v1/audio/transcription-tasks/{task_id}
       ← {status, result: [{start_time, end_time, text}]}
```

**关键事实**：火山 ASR 收的是 **URL**，不是文件 —— 它要求音频有一个**公网可访问地址**。这是 S3 在上游架构里存在的**唯一理由**。

### 2.2 改造后

```
浏览器 → presigned PUT → RustFS（上传音频 mp3）        ← 这一步保留
后端   → POST http://asr:8000/transcribe  {filename}
       ← 返回 task_id
ASR    → 自己从 RustFS get_object 取音频 → faster-whisper 转写 → 毫秒时间戳
前端   → 轮询 GET /api/v1/audio/transcription-tasks/{task_id}   ← 契约完全不变
```

**「公网 URL」这一环彻底消失** —— 音频从未离开本机。

### 2.3 必须保住的返回契约

```python
result = [{"start_time": <毫秒>, "end_time": <毫秒>, "text": str}, ...]
返回体 = {"status": "finished", "result": result}
```

**单位是毫秒，不是秒。** 前端 `index.vue` 用 `/ 60000` 和 `/ 1000` 做换算。faster-whisper 返回的是**秒**，所以 ASR 侧必须 `int(seg.start * 1000)`。

实测验证：8 秒音频返回 `end_time: 29980`（对应 whisper 的 `29.98` 秒）。

### 2.4 为什么 ASR 不直接复用后端给的 presigned URL

因为**容器里的 `127.0.0.1` 指向它自己**。后端签发的 URL 里烧的是宿主机视角的 `127.0.0.1:9000`，在 ASR 容器内访问会打到 ASR 自己身上。

所以 ASR 用自己配置的 `S3_ENDPOINT=http://rustfs:9000` 直接 `get_object`。这比「给 ASR 加 `extra_hosts` 再签一次」干净。

## 3. 核心改造二：对象存储从 TOS 换到 RustFS

### 3.1 为什么 S3 不能整体去掉

上传路径是 **浏览器 XHR 直传**（`frontend/src/apis/http.ts` 的 `xhr.open('PUT', url)`）。去掉桶，浏览器就没有落点了。

**能去掉的只有「ASR 递公网 URL」那一跳。**

### 3.2 为什么是 RustFS

最初尝试用 **OpenList**（alist 社区分支，NAS 上已有）。实测结果：

| 探测项 | 结果 |
|---|---|
| SigV4 签名 | 可用（AK/SK 有效，ListBuckets 成功） |
| virtual-hosted 寻址 | DNS 无法解析 |
| ListObjects / PUT / GET | 未通过 |

OpenList 的 S3 实现是 rclone `serve s3` 的移植，官方包说明原文是 *"Package s3 implements a fake s3 server"*，文档只承诺 **list / get / put / del** 四种操作。boto3 隐式使用的 multipart、HeadObject、checksum 都在承诺之外。

放弃理由：**假 S3 的未文档化契约有静默截断大文件的风险**，且本项目音频不出本机，聚合远端驱动这个核心价值用不上。

在 RustFS 与 MinIO 之间选 RustFS 的**决定性理由是 Apache-2.0**（MinIO 是 AGPLv3）。

### 3.3 RustFS 实测结果

| 探测项 | 结果 |
|---|---|
| 签名（AK/SK） | PASS |
| virtual-hosted 寻址 | PASS（boto3 在 IP 端点下自动降级为 path-style 兜住） |
| presigned PUT（浏览器直传模拟） | HTTP 200 |
| presigned GET | 字节一致 |
| SDK `get_object` | PASS |

### 3.4 浏览器直传必须配桶级 CORS

**这是最容易踩的坑。** 前端在 `localhost:5173`，要 PUT 到 `127.0.0.1:9000`，属跨源。

RustFS 的 CLI **没有任何 CORS 开关**（`server --help` 全文翻过），但支持 S3 标准的 bucket 级 CORS。必须执行一次：

```powershell
python scripts\init_rustfs.py
```

未配置时的症状是「上传卡住 + 网络错误」，**而后端日志完全正常**（因为请求根本没到后端）。

**命令行工具不做 CORS 检查。** 用 curl / boto3 测 PUT 会返回 200，让人误判「上传能用」。必须用带 `Origin` 头的请求测 OPTIONS 预检。

**CORS 配置存在数据卷里。** 换新卷或清库后必须重跑 `init_rustfs.py`。

## 4. 核心改造三：哈希复用（跳过 ASR，只重跑 AI 总结）

### 4.1 上游原有逻辑及其问题

上游已有 MD5 去重，但存在**前端 IndexedDB**（`frontend/src/utils/db.js`），且命中后直接中止：

```js
// 上游 index.vue:140-146
const exists = await checkTaskExistsByMd5AndStyle(audioMd5, style.value)
if (exists) {
  ElMessage.warning('该音频已以相同风格处理过，请在历史记录中查看')
  return   // 直接 return
}
```

问题：**换台机器、换个浏览器、清一次缓存，去重就失效了。** 而且「已处理过」就直接拒绝，用户想换个文档风格都不行。

### 4.2 改造后：三级复用链

```
(1) 查 S3 桶（跨机器有效）
      GET /api/v1/audio/transcripts/{md5}.mp3
      命中 → 直接拿 segments JSON
(2) 查 IndexedDB（本机历史）
      命中 → 用本地记录
(3) 都没有 → 走完整流程
      getAudioUploadUrl → uploadFile → submitAsrTask → pollAsrTask
```

命中 (1) 或 (2) 时，**跳过 ASR，直接进入 AI 总结环节**。

### 4.3 桶里存的是 segments JSON

不是纯文本。因为下游要生成 `[00:23-00:28]` 这样的时间戳分段，**必须保留毫秒时间戳**。

```json
{
  "filename": "abc123.mp3",
  "language": "zh",
  "duration": 240.5,
  "result": [{"start_time": 0, "end_time": 29980, "text": "..."}]
}
```

存放位置：`transcripts/{md5}.json`（与音频 `{md5}.mp3` 同哈希，复用同一个键）。

## 5. 核心改造四：自动清理

### 5.1 为什么要做

桶膨胀是**慢性问题** —— 靠人记得去点「清空」按钮，基本等于不会清。

### 5.2 策略：按对象年龄

| 配置项 | 默认 | 说明 |
|---|---|---|
| `RETENTION_DAYS` | `1` | 超过 N 天没被碰过的产物就删。**`0` = 关闭清理**（不是「立即删除」） |
| `CLEANUP_INTERVAL_SECONDS` | `3600` | 扫描间隔 |
| `CLEANUP_INITIAL_DELAY_SECONDS` | `300` | 启动后首次扫描延迟 |

**判据用 S3 的 `LastModified`**，不是文件系统的 mtime —— 后者改不动 S3 元数据里的值。

实测踩过的坑：用 `touch` 改宿主机文件时间**不会**影响 `LastModified`。要构造过期对象，得用一个很小的 `RETENTION_DAYS`（如 `0.0002` 天约 17 秒）。

### 5.3 失败处理

- 落桶失败 ⇒ **只 warning，不阻断转写**。转写已经成功，桶写不进只是丢掉复用能力，不该转嫁成转写失败。
- 清理异常 ⇒ **不能让定时器线程死掉**，否则桶再也无人回收。

**`backend/env.py` 有 fallback 链**：`STORAGE_X = os.getenv("TOS_X") or os.getenv("STORAGE_X")` —— **`TOS_*` 优先于 `STORAGE_*`**。如果环境里残留旧的 `TOS_ENDPOINT`，它会「赢」，导致悄悄连回云端。compose 里已显式把这些变量置空。

### 新增变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `ASR_BASE_URL` | `http://asr:8000` | 后端转发目标 |
| `S3_ENDPOINT` | `http://rustfs:9000` | ASR 取对象用（**容器内**视角） |
| `RETENTION_DAYS` | `1` | 见 5.2 |
| `CLEANUP_INTERVAL_SECONDS` | `3600` | 见 5.2 |

**S3 地址有两个「视角」**，一个变量喂不饱：

| 谁 | 在哪 | 它眼中的 S3 | 用途 |
|---|---|---|---|
| 浏览器 | 宿主机 | `http://127.0.0.1:9000` | 直传（上传） |
| 后端 | backend 容器 | 用不到 | 只签发 URL，从不传输字节 |
| ASR | asr 容器 | `http://rustfs:9000` | 取对象（下载） |

## 8. 已知未验证项

诚实记录，未测就是未测：

- **真实语音的转写准确率** —— 端到端测试用的是正弦波（whisper 对非人声会输出 `Thanks for watching!` 这类幻觉），只验证了链路，没验证准确度
- **前端 UI 的人工点击路径** —— 代码审查通过、Vite 编译通过、页面 200，但没有真人在浏览器里完整点一遍
- **LLM 环节的实际生成质量** —— 同上
- **多副本部署** —— ASR 的任务表是**进程内内存态**（`TASKS: Dict`），单 worker 才正确。要水平扩展必须换成 Redis
- **上游 `backend/Dockerfile:38-48` 的硬编码 `"xxx"`** —— 未被修复，只是靠 compose 正确注入 env 绕开了
