## 3. 桶选型：为什么是 RustFS（**已定案**）

### 3.1 探测结论：OpenList 不是不行，是不该用

用户最初要求「桶最好是本地的 openlist 桶（来自 alist）」。**实测后改判**。

**实测方法**：手写 SigV4 脚本 `scripts\probe_openlist_s3.py`（仅 stdlib + requests，**不经 boto3**）打 OpenList 的 S3 端口。

**结果（7 项，2 通过）**：

| 项 | 结果 | 说明 |
|---|---|---|
| Q0 端点可达 | ✅ PASS | 未签名返回 `InvalidAccessKeyId` |
| **Q1 SigV4 签名** | ✅ **PASS** | **签名是对的！**成功 ListBuckets，返回真实桶（含 `legado`），Owner `GoFakeS3` |
| Q2 virtual-hosted 寻址 | ❌ FAIL | `media2doc.192.168.50.7` **无法解析**（DNS） |
| Q3a/b/c/d（list/put/get） | ❌ FAIL | 全部 `NoSuchBucket` |

**★ 关键澄清**：Q3 全挂的原因是**桶名 `media2doc` 是我编的**，OpenList 上并不存在 —— **不是签名失败**。Q1 已证明签名完全可用。

**⇒ 所以 OpenList 大概率能用**（建个真桶、`addressing_style` 改 `path` 即可）。**但用户主动放弃，理由成立**（用户原话：「我何必纠结 openlist 呢？有没有能用的？」）：

1. **它是"假 S3"** —— 官方 package 说明原文 *"Package s3 implements a **fake** s3 server for openlist"*，是 rclone `serve s3` 移植；官方文档只承诺 **list/get/put/del** 四个操作。
2. **静默失败风险** —— boto3 隐式使用的 multipart 上传、`HeadObject`、checksum 头**都在承诺之外**。大音频静默截断比明确报错更糟。
3. **双层间接** —— OpenList 的价值是**聚合远端驱动**（`legado` 就是），而本项目音频**全程不出本机**，加聚合层只有开销没有收益。

### 3.2 选定 RustFS（非 MinIO）

| 维度 | RustFS | MinIO |
|---|---|---|
| **协议** | **Apache-2.0** | **AGPLv3** |
| S3 完整度 | 真 S3（含 multipart） | 真 S3 |
| 地址风格 | 支持 path **与** virtual-host（有专门的 Virtual-Host Access 文档） | path/virtual |

**选 RustFS 的决定性理由是 Apache-2.0**：与工作区其余组件同协议族，无 copyleft 传染问题。

> **⚠️ 一次自我更正**：本会话早前曾说「MinIO 控制台功能被逐步剥离」。**该说法未在本会话验证**，已收回。
> 可核查的 MinIO 异议只有两条：**AGPLv3**，以及 **2025 年社区版被功能门槛化**（控制台管理功能移入付费 AIStor）。

**RustFS 关键事实**（出自官方文档，**非**本机实测）：

| 项 | 值 |
|---|---|
| 镜像 | `rustfs/rustfs:latest` |
| S3 API 端口 | **9000** |
| Console 端口 | **9001** |
| 凭据变量 | `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY` |
| **默认凭据** | **`rustfsadmin`/`rustfsadmin`（公开！必须改）** |
| 容器 UID | **10001**（绑定宿主目录必须 `chown 10001:10001`） |
| 文件注入 | `RUSTFS_ACCESS_KEY_FILE` / `RUSTFS_SECRET_KEY_FILE` |
| ⚠️ 访问键限制 | **不能含 `/`** —— SigV4 会把 AK 嵌进 credential scope，含斜杠会解析错。**建议只用大写 A-Z + 0-9** |

> **未验证项**：上述 RustFS 细节**全部来自官方文档**，本机**未跑过 RustFS**。
> 装好后必须用 `scripts\probe_openlist_s3.py`（改 endpoint 即可复用）打一遍，**以实测为准**。

## 4. 改动清单（改哪个文件、改什么）

### 4.1 `backend\routers\audio.py` —— **重写两个端点**（改动量：中）

**保留契约**（前端只认这个，见 §2）：
```
POST /api/v1/audio/transcription-tasks           → {"data":{"task_id": ...}}
GET  /api/v1/audio/transcription-tasks/{task_id} → {"data":{"status": ..., "result": [...]}}
```

**要改成**：不再调 `openspeech.bytedance.com`，改调本地 ASR service。

**⚠️ 必须解决的架构冲突：异步契约 vs 同步引擎**

- 原设计：火山 ASR 是**异步两段式**（提交→轮询），提交立即返回 `task_id`
- faster-whisper 是**同步**的，一次 `transcribe()` 可能跑**数秒到数分钟**

**若直接在 `create_transcription_task` 里同步跑 faster-whisper**：
- HTTP 请求会一直挂着直到转写完成
- `http.ts:30` 的 `timeout: 240000`（**4 分钟**）会被长音频冲破
- 前端的进度步骤会长时间无响应

**⇒ ASR service 内部必须自建「任务表 + 后台线程」**，维持「提交立即返回 task_id、轮询查状态」的语义。
**这是本次改造最容易低估的工作量。**

**字段单位转换（§2 的坑）**：
```python
# faster-whisper 的 segment：start/end 单位是「秒（float）」
# 契约要求「毫秒（int）」—— 必须 ×1000
{"start_time": int(seg.start * 1000), "end_time": int(seg.end * 1000), "text": seg.text}
```

### 4.2 `backend\Dockerfile` —— **加 CUDA**（改动量：中）

**现状**：`python:3.11-slim`，**纯 CPU**。
**目标**：能跑 faster-whisper + CUDA。

**⚠️ 真正的风险点不是"加 CUDA"，是「版本三角」**：
`CUDA 基础镜像的 Python 版本` ↔ `ctranslate2 的 wheel` ↔ `faster-whisper 的要求`

- CUDA 镜像的 Python 版本**由 CUDA tag 决定，不是自由选**
- `ctranslate2` wheel 是**绑定约束**（决定 CUDA 版本与 Python 版本）
- 交接文档说「加 faster-whisper 不会依赖地狱」—— **那句话针对的是现有 9 个包，不覆盖新增的 CUDA 栈**。这是目前**最大的未验证风险**。

**待定**：优先 `nvidia/cuda:12.x-runtime` + pip 装 `ctranslate2`，还是直接用预装好的镜像。**需要先验证 wheel 可用性再定。**

### 4.3 `backend\utils\s3.py` —— **改客户端配置**（改动量：小）


- `addressing_style` → **`"path"`**（RustFS 虽然两种都支持，但 path 在 `127.0.0.1` 上更稳，避免 DNS 依赖）

**⚠️ 一个必须处理的隐蔽坑 —— `env.py` 的 fallback 链**：

## 8. 功能增强：桶内转写复用 + 自动清理（2026-10-11 追加）

用户在本轮提出四条需求，全部落地并实测。

### 8.1 为什么要做：转写是整条链路里最贵的一步

一次完整流程的成本分布（本机 4060 实测感受）：

| 步骤 | 代价 | 可复用？ |
|---|---|---|
| 抽帧（浏览器 ffmpeg.wasm） | 高，纯 CPU | 否（帧随视频走） |
| **ASR 转写（GPU）** | **最高**，几分钟 | **是** ← 只与音频有关 |
| AI 总结（DeepSeek） | 低（网络 + token） | 否（换 prompt 就该重跑） |

⇒ **把转写产物存起来**，重跑同一视频时直接跳过最贵的一步。
注意「复用转写」与「跳过总结」是**两件事**：命中哈希应该只跳过转写，
**总结照跑**（用户很可能就是想换个风格重出）。

### 8.2 转写产物落桶（`src\asr\app.py`）

转写完成时，把 **segments 数组 JSON**（带毫秒时间戳）写进桶：

```
s3://media2doc/transcripts/<audio_key>.json
```

**为什么存 segments 而不是纯文本**：目标产物里有 `[00:23-00:28]` 这种**分段标注**，
纯文本丢了时间戳就再也拼不回来。JSON 同时兼容「只要文字」的用法（取 `.text`）。

落点：`app.py` 转写成功分支，与 `TASKS[task_id]` 赋值同批。
**写入失败不阻断转写** —— 缓存是加速手段，不是正确性依赖。

### 8.3 三个新端点（ASR 侧）

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/transcripts/{key}` | 按 key 取转写 JSON（命中复用） |
| `GET` | `/transcripts` | 列出桶内全部转写产物 |
| `DELETE` | `/transcripts/{key}` | 删单个（桶侧） |

后端 `audio.py` 透传为 `/api/v1/audio/transcripts*`，共 **7 个端点**。

### 8.4 前端复用链（`src\patches\transcriptService.ts` + `index.vue` 区间替换）

获取顺序改为 **桶 → IndexedDB → 跑 ASR**：

```
getTranscriptFromBucket(key)   ① 桶（跨设备可信，ASR 落盘的事实来源）
  ↓ 未命中
getAnyTaskByMd5(md5)           ② IndexedDB（本地兜底，老数据）
  ↓ 未命中
submitAsrTask → pollAsrTask    ③ 真的跑一遍 GPU
```

**同时修掉一个上游 bug**（`index.vue:140` 附近）：
原实现在「命中同 md5+风格」时**弹个警告就 `return`**，什么都不做。
用户上传一个处理过的视频，期望的是**给我一份新的总结**，
而不是被推回去手工翻历史记录。改为：命中只意味着「跳过 ASR」，**继续往下生成总结**。

⚠️ **复用路径必须显式收尾步骤状态**：第 2 步（上传）被整段跳过，
若不手动 `updateStepStatus(2, 'success')`，步骤条会**永远停在「处理中」**。

### 8.5 自动清理（用户定案：按寿命，不是到期清空）

用户的原话（m00690）："**默认 1d，然后 0 的话是不清除 是按寿命，不是按到期清除所有**"

| 配置 | 默认 | 语义 |
|---|---|---|
| `RETENTION_DAYS` | **1** | 对象寿命（天）。**0 = 关闭清理**（桶只增不减） |
| `CLEANUP_INTERVAL_SECONDS` | 3600 | 扫描间隔 |
| `CLEANUP_INITIAL_DELAY_SECONDS` | 300 | 启动后首次清理的延迟 |

**判定逻辑**（`app.py` `purge_expired()`）：

```python
cutoff = datetime.now(timezone.utc) - timedelta(days=RETENTION_DAYS)
for obj in list_objects_v2(...):
    if obj["LastModified"] >= cutoff:   # ← 逐个比寿命，不是一刀切
        continue
    s3.delete_object(...)
```

**三个设计决定及其理由**：

1. **用 S3 的 `LastModified`，不用本地文件时间。**
   实测教训：`touch` 改宿主机文件的 mtime **对判定毫无影响** ——
   RustFS 把时间存在自己的元数据（`xl.meta`）里。
   S3 侧的时间是唯一可信源（本地时钟、容器时区都可能不对）。

2. **`0` 解释成「关闭」而不是「立即过期」。**
   两者字面很像，后果差一个数量级：把 0 当成「全删」，用户手滑填 0 就丢整个桶；
   当成「关闭」，最坏只是不清理。**不对称的风险要选保守那侧。**

3. **同时清 mp3 和转写 JSON，不分开。**
   否则会留下「转写在、音频没了」的半残状态 —— 命中缓存后去取音频会 404，
   **而错误点离真正的原因很远**，排查代价高于多删一个文件。

**为什么不做「清空」按钮**：用户先提了双按钮方案，随后自己改成定时清理（m00596）。
定时方案更好 —— 桶膨胀是**慢性问题**，靠人记得去点按钮 ≈ 不会清。

### 9.5 ⚠️ 一个必须记下的 storage 布局事实

RustFS 落盘后，桶内**不是标准 S3 对象布局**：

```

/data/media2doc/e2etest...mp3/xl.meta                ← 元数据
```

标准 S3 里 `xxx.mp3` 应是**对象**，这里它是**目录**（MinIO 式分片+元数据布局）。

**对功能无影响**（S3 API 层完全正常，5/5 测试通过），
但**不要把桶目录当普通文件树去搬/备份** —— 必须走 S3 API 或整体拷贝。
